# ADR 0004: Use k3d for Local Kubernetes Runs

- Status: Accepted
- Date: 2026-07-15

## Context

Students need to reproduce a Run without renting a cluster. The platform also
needs a server path, but maintaining kind and k3d as two local implementations
would split testing and documentation. A local registry must be reachable from
Kubernetes and the BuildKit/Fixture workflow without using `localhost` inside a
Pod.

## Decision

Use k3d for local development and a single-node k3s installation for the
server demonstration path. The k3d bootstrap creates the cluster and an
in-network `ai-registry:5000` registry, maps the Kubernetes API to host port
6550, and produces a dedicated Worker kubeconfig. Local Preview access uses a
host-managed port-forward; the platform does not return a container-only
port-forward URL.

Run namespaces use Restricted Pod Security, resource limits, non-root
containers, disabled ServiceAccount token mounting and no hostPath, privileged
or Docker Socket access. k3d's default NetworkPolicy behavior is not used as a
P0 isolation claim.

The rootless BuildKit POC did not pass in the available runtime
(`fork/exec /proc/self/exe: operation not permitted`). Therefore dynamic
BuildKit construction is P1. P0 uses a digest-pinned, platform-controlled
Fixture image and must label the run `BUILD_MODE=FIXTURE`; this ADR does not
claim that dynamic untrusted Dockerfile builds are safe or complete.

## Consequences

The local path has low cost and one documented Kubernetes implementation. k3d
is still not a production sandbox, and Fixture mode does not prove arbitrary
source builds. A future dynamic-build milestone must repeat the Restricted PSA,
push, pull and digest deployment gate before being promoted to P0.

## Verification

- `infra/k3d/bootstrap.sh` configures the cluster API and in-network registry.
- `infra/k3d/README.md` documents the registry address and BuildKit gate.
- `infra/k3d/buildkit-smoke-test.sh` is the executable POC path.
- `packages/k8s/src/k8s.test.ts` and `runtime.test.ts` cover restricted resource
  construction and ownership-safe cleanup.
- The remote test on 2026-07-15 showed k3s API readiness but Pod sandbox/cgroup
  permission failures; it is recorded as an environment limitation, not a
  successful Preview deployment.
